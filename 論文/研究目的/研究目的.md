# 第二章：研究目的

## 2.1 問題描述

本專題擬解決以下核心問題：

### 2.1.1 藥物辨識問題

台灣核准的藥物種類繁多（本資料庫收錄 4,419 筆），其中大量口服固體製劑在外觀上高度相似——白色圓形錠劑佔比最高。當藥物脫離原包裝（如分裝藥盒、藥袋散落）後，一般使用者（尤其年長者）極難僅憑外觀辨別藥物身份。錯誤的藥物辨識可能導致誤服、漏服，甚至產生嚴重的藥物不良反應。

### 2.1.2 用藥管理問題

多重用藥（Polypharmacy）在年長者群體中極為普遍。同時服用 5 種以上藥物時，藥物交互作用風險顯著上升。現有用藥管理工具多為單純的「鬧鐘提醒」功能，缺乏：
- 藥物辨識與用藥紀錄的整合
- 藥物交互作用的自動檢查
- 過敏藥物的主動警告
- 針對年長者的友善操作介面

### 2.1.3 藥物資訊取得問題

台灣藥物相關資訊分散在多個政府網站：
- **衛生福利部食品藥物管理署（TFDA）**：提供藥物許可證資料、適應症、主成分等
- **中央健康保險署（NHI）**：提供健保藥品查詢
- 各醫療院所的用藥指導資訊

使用者需要逐一查詢不同網站，操作繁複且資訊格式不統一，對年長者更是一大障礙。

## 2.2 前人解決方法

### 2.2.1 傳統影像辨識方法

| 方法 | 技術 | 優點 | 缺點 |
|------|------|------|------|
| **OpenCV 特徵比對** | SIFT/SURF/ORB 特徵描述子 + KNN 匹配 | 不需 GPU、可離線運行 | 需大量標註資料、新藥需重訓、對光線敏感 |
| **CNN 分類模型** | 卷積神經網路（ResNet/EfficientNet）| 可達高準確度 | 訓練成本高、新增藥物需重新訓練、需 GPU |
| **YOLO 物件偵測** | You Only Look Once | 可同時偵測多顆藥物 | 僅偵測位置，仍需分類模型配合 |

**前版系統（MUS_Project v1）** 即採用 OpenCV 本地特徵比對方案，存在以下問題：
- 部署複雜度高（需安裝多個 CV 模型）
- 辨識準確度受限於特徵描述子的表達能力
- 新增藥物時需手動擷取特徵並重新訓練
- 響應時間較長（2-5 秒）

### 2.2.2 雲端 AI 辨識方法

| 方法 | 技術 | 優點 | 缺點 |
|------|------|------|------|
| **Google Cloud Vision** | GCP Vision API 標籤偵測 | 通用物件辨識能力強 | 非專為藥物設計、標籤粒度不足 |
| **直接 LLM 辨識** | 直接向 GPT-4V/Gemini 詢問 | 靈活度高、無需訓練 | **AI 幻覺嚴重**——會生成不存在的藥物名稱 |
| **專業藥物辨識 App** | 如 Medscape、Epocrates | 資料庫完整 | 多為英文介面、不支援台灣藥物、費用高 |

### 2.2.3 前人方法的核心問題

1. **AI 幻覺問題**：直接使用 LLM 進行藥物辨識，模型會「自信地」生成聽似合理但實際不存在的藥物名稱，導致後續資料庫查詢完全失敗。實測顯示，直接 LLM 辨識的資料庫匹配率僅約 30%。

2. **冷啟動問題**：CNN/OpenCV 方案對於新上市藥物或資料庫中缺少圖片的藥物無法辨識，需等待模型更新。

3. **單一功能侷限**：多數藥物辨識工具僅提供「辨識」功能，不涵蓋用藥管理、安全檢查等後續流程。

## 2.3 本文解決構想

### 2.3.1 核心構想：RAG（檢索增強生成）藥物辨識

本研究提出將 RAG 技術應用於藥物辨識的創新方法。核心思想是：**不讓 AI 自由發揮，而是約束其僅從已知藥物資料庫中選擇**。

```
【傳統 LLM 方法（存在幻覺問題）】
藥物照片 → LLM 自由生成 → "阿斯匹林" → 查資料庫 → 可能查無此藥

【本研究 RAG 方法（解決幻覺問題）】
資料庫 4,419 筆藥物特徵 ─┐
                           ├→ LLM 從清單中選擇 → 直接回傳藥物 ID → 必然存在於資料庫
藥物照片 ─────────────────┘
```

具體而言：
1. 從資料庫提取藥物的關鍵視覺特徵（許可證字號、中文名、形狀、顏色、刻印標記）
2. 將特徵清單與待辨識圖片共同作為 Prompt 輸入 Gemini Vision API
3. 要求 AI 模型「從列表中選擇最匹配的藥物」而非自行命名
4. AI 回傳的結果必然存在於資料庫中，從根本上解決幻覺問題

### 2.3.3 技術創新構想

| 創新點 | 構想 | 解決的問題 |
|--------|------|-----------|
| **RAG 藥物辨識** | 將資料庫特徵作為 LLM 上下文，限定輸出範圍 | AI 幻覺、匹配率低 |
| **多層 AI 路由** | Primary→Secondary→Fallback 鏈 + 熔斷器 | API 服務不穩定 |
| **OCR 總量驗證** | dose × freq × days 交叉驗證 | OCR 數值提取錯誤 |
| **四層安全檢查** | 過敏→重複→交互→分級的串聯式檢查 | 用藥安全風險 |
| **自動資料補充** | 爬蟲 + 快取 + 批次更新 + 指數退避 | 藥物資訊不完整 |
| **年長者介面** | 大字體 + 高對比 + 三步操作 + SPA | 使用門檻高 |
