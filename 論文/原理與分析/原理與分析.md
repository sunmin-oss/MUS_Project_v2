## 3.3 RAG 藥物辨識原理與分析（理論創新）

### 3.3.1 原理說明

RAG（Retrieval-Augmented Generation，檢索增強生成）是一種結合「資訊檢索」與「文本生成」的 AI 技術。其核心思想是：在生成（Generation）之前，先從外部知識庫中檢索（Retrieval）相關資訊作為上下文，引導生成模型產出更準確、更可靠的結果。

**本研究的 RAG 應用原理：**

```
                    ┌─────────────────────────┐
                    │     藥物資料庫           │
                    │  ┌───────────────────┐  │
                    │  │ 4,419 筆藥物資料   │  │
                    │  │ • 許可證字號       │  │
                    │  │ • 中文名稱         │  │
                    │  │ • 形狀、顏色       │  │
                    │  │ • 刻印標記 (正/反) │  │
                    │  └─────────┬─────────┘  │
                    └─────────────┼────────────┘
                                  │ ① 特徵檢索
                                  ▼
                    ┌─────────────────────────┐
                    │  特徵清單（500 筆取樣）  │
                    │  ID:1 | 福元蘇打錠 |    │
                    │  圓形 | 白色 | F-500    │
                    │  ...                     │
                    └─────────────┬────────────┘
                                  │ ② 注入上下文
                                  ▼
┌──────────────┐    ┌─────────────────────────┐
```

### 3.3.2 RAG vs 傳統方法分析

| 比較維度 | 傳統 LLM 直接辨識 | RAG 增強辨識（本研究） |
|---------|------------------|---------------------|
| 輸出範圍 | 無限制（任意藥物名） | 限定在資料庫內的藥物 |
| AI 幻覺 | **嚴重** — 會生成不存在的藥名 | **有效解決** — 只能從已知清單選擇 |
| 資料庫匹配率 | ~30% | **90%+** |
| 辨識準確度 | ~40% | **85%+** |
| 新增藥物 | 不需額外處理（但可能幻覺） | 只需更新資料庫，無需重訓模型 |
| 計算成本 | 低（單次 API 呼叫） | 略高（需附帶特徵清單） |

### 3.3.3 特徵提取策略

本系統從資料庫中提取以下視覺相關特徵作為 RAG 上下文：

```python
def get_drug_features_for_rag(self, sample_size=500):
    """取得藥物特徵清單供 RAG 使用"""
    cursor.execute("""
        SELECT id, license_number, chinese_name, english_name,
               shape, color, mark, label_front, label_back
        FROM drugs
        WHERE chinese_name IS NOT NULL
        LIMIT ?
    """, (sample_size,))
    
    # 格式化為 AI 易理解的結構化文字
    drug_list = []
    for drug in cursor.fetchall():
        info = f"ID:{drug.id} | 許可證:{drug.license_number}"
        info += f" | 名稱:{drug.chinese_name}"
        if drug.shape: info += f" | 形狀:{drug.shape}"
        if drug.color: info += f" | 顏色:{drug.color}"
        if drug.mark:  info += f" | 刻印:{drug.mark}"
        drug_list.append(info)
    return "\n".join(drug_list)
```

**設計決策：**
- `sample_size=500`：平衡上下文長度與覆蓋率，避免超出 API Token 限制
- 優先提取視覺特徵（形狀、顏色、刻印），因為這些是 Vision API 可直接比對的屬性
- 使用管線分隔的平面文字格式，而非 JSON，以減少 Token 消耗

### 3.3.4 提示詞工程（Prompt Engineering）

**RAG 辨識提示詞設計原則：**

1. **角色設定**：明確指定 AI 為「藥物識別專家」
2. **約束條件**：強調「必須從列表中選擇，不可自行創造藥物名稱」
3. **匹配優先順序**：刻印標記 > 顏色 > 形狀（因刻印具有最高辨別度）
4. **輸出格式**：嚴格要求 JSON 格式，含 drug_id、confidence、reason 欄位
5. **信心度上限**：強制限定在 0.98 以下（不允許 100% 確定）

### 3.4.2 總量驗證演算法（創新）

處方箋 OCR 常見的錯誤是小數點遺失（如 4.5 被識別為 45）。本研究提出基於劑量資訊的交叉驗證機制：

```python
# 頻率解析（支援中英文）
FREQUENCY_MAP = {
    'QD': 1, 'BID': 2, 'TID': 3, 'QID': 4,
    'Q4H': 6, 'Q6H': 4, 'Q8H': 3, 'Q12H': 2,
    '每日一次': 1, '每日兩次': 2, '每日三次': 3, '每日四次': 4,
    '三餐飯後': 3, '早晚': 2, '睡前': 1, ...
}

# 計算期望總量
expected_total = dose_per_time × frequency_per_day × days

# 驗證與修正
if abs(actual_total - expected_total) / expected_total > 0.3:
    # 嘗試修正：可能是小數點遺失
    if abs(actual_total / 10 - expected_total) < tolerance:
        corrected_total = actual_total / 10  # 45 → 4.5
```

## 3.5 多層 AI Provider 路由架構（設計方法創新）

### 3.5.1 架構設計

為確保 AI 服務的高可用性，本系統設計了三層鏈式 AI 服務路由，搭配熔斷器模式：

```
┌─────────────────────────────────────────────────────────┐
│                  RecognizerRouter                        │
│                                                          │
│  ┌──────────┐  失敗  ┌──────────┐  失敗  ┌──────────┐ │
│  │ Primary  │──────→│ Secondary│──────→│ Fallback │ │
│  │ Gemini   │       │ Gemini   │       │ OpenAI   │ │
│  │ Key A    │       │ Key B    │       │ GPT-4o   │ │
│  └──────────┘       └──────────┘       └──────────┘ │
│       │                                               │
│       ▼                                               │
│  ┌──────────────────┐                                 │
│  │   熔斷器 (Circuit Breaker)                         │
│  │  • 連續失敗 ≥ 3 次 → 開啟熔斷                      │
│  │  • 冷卻期 300 秒 → 直接跳至末層                    │
│  │  • 冷卻結束 → 半開狀態，嘗試恢復                    │
│  └──────────────────┘                                 │
│                                                          │
│  ┌──────────────────┐                                 │
│  │   錯誤分類                                          │
│  │  • Retryable: 超時/5xx → 重試當前層                │
│  │  • Quota: 429 → 立即切備援                          │
│  │  • Permanent: 400/401 → 不切換（設定錯誤）          │
│  └──────────────────┘                                 │
└─────────────────────────────────────────────────────────┘
```

### 3.5.2 設計理由

- **Primary/Secondary 使用不同 API Key**：避免單一 Key 的請求配額限制影響服務
- **Fallback 使用不同 AI Provider**：避免單一服務商的全域故障（如 Google API 全面停機）
- **熔斷器模式**：避免在 API 明確故障時持續發送無效請求，浪費時間與費用

### 3.7.2 批次更新效能優化

| 優化項目 | 優化前 | 優化後 | 效果 |
|---------|--------|--------|------|
| 瀏覽器管理 | 每筆藥物啟動/關閉 Chromium | **共用單一 Browser 實例** | 省去每次 ~2s 啟動時間 |
| 頁面等待 | `wait_for_timeout(3000)` 固定等待 | **`wait_for_selector` 精確等待** | 頁面載入即繼續，不浪費時間 |
| 資料庫連線 | 每筆開關 SQLite 連線 | **共用連線 + WAL 模式** | 減少 I/O 開銷 |
| 請求延遲 | 固定 3.0 秒 | **最低 0.3 秒 + 指數退避** | 成功時快速，失敗時自動減速 |
| Debug 輸出 | 每筆寫入 debug 檔案 | **移除 debug 寫檔** | 減少磁碟 I/O |

**指數退避策略：**
```
成功時：delay = 基準延遲（0.3~3.0 秒）
連續失敗 1 次：delay = 基準 × 2¹
連續失敗 2 次：delay = 基準 × 2²
...
最大延遲上限：30 秒
成功後重設退避計數器
```

## 3.9 安全機制設計

### 3.9.1 認證與授權流程

```
┌──────┐    POST /auth/login     ┌───────────┐
│Client│──────────────────────→│  Flask    │
│      │    {username, password} │  Server   │
│      │                         │           │
│      │    ← 200               │  bcrypt   │
│      │    {access_token (15m), │  verify   │
│      │     refresh_token (7d)} │           │
│      │                         └───────────┘
│      │
│      │    GET /api/user/meds
│      │    Authorization: Bearer {access_token}
│      │──────────────────────→ JWT 驗證 → 回傳資料
│      │
│      │    POST /auth/refresh
│      │    Authorization: Bearer {refresh_token}
│      │──────────────────────→ 核發新 access_token
│      │
│      │    POST /auth/logout
│      │──────────────────────→ Token 加入黑名單
└──────┘
```

### 3.9.2 多層安全防護

| 層級 | 機制 | 說明 |
|------|------|------|
| 網路層 | Nginx Rate Limiting | 30r/s + burst=20 |
| 應用層 | Flask-Limiter | 全域 200/min，辨識 30/min |
| 認證層 | JWT + 黑名單 | Access Token 15 分鐘過期 |
| 授權層 | `is_admin` 裝飾器 | 管理功能僅限管理員 |
| 密碼層 | bcrypt | Salt + Hash，抵抗彩虹表攻擊 |
| 傳輸層 | HTTPS（生產環境） | 加密所有通訊 |
| 輸入層 | 檔案類型/大小驗證 | 防止惡意檔案上傳 |
| Header 層 | X-Frame-Options 等 | 防止 XSS、Clickjacking |
