# 專題口試—評審可能提問回答

> **口試資料口徑**：截至目前，實際查詢的 `drug_recognition.db` 為 4,423 筆藥品；`medicine_photos` 目錄為 4,776 張圖片。正式論文若沿用 4,419 或 4,416 筆，應先確認資料庫匯入與去重時點並統一修正。對於 85%→93%、14.3% OpenCV Top-1 等數字，若原始逐筆紀錄未保存，口試中不宜作為已驗證結論呈現。

## 第 1 題｜為什麼選擇 RAG？

### 回答

我們不是以 RAG 替代 Gemini Vision，而是將兩者分工：**Gemini Vision 負責理解圖片及文字；RAG 提供受控的藥品候選資料庫與可追溯的資料來源。**

直接呼叫 Gemini 時，模型可能依照訓練資料自由回答，也可能產生不存在或名稱相近的藥品。本系統先讓 Gemini 分析圖片中的刻印、形狀與顏色，再從 SQLite 藥品資料庫取得候選資料；在第一階段也會限制結果與資料庫中的藥品紀錄連結。這能降低模型自由生成藥名的風險，並讓辨識結果可連到藥品 ID、許可證、成分及後續安全檢查。

需要說明的是，RAG 無法保證完全降低幻覺。若資料庫候選遺漏正確藥品、資料本身錯誤，或模型選錯候選，結果仍可能錯誤。因此 RAG 應視為「資料約束與可追溯性機制」，不是錯誤保證機制。

### 評審追問

**RAG 是否真的能降低幻覺？**  
可以降低模型憑空產生藥名的機會，但不能消除錯誤。第一階段會優先由刻印搜尋資料庫；第二階段是把候選清單放入提示詞，仍需 Gemini 選擇。因此幻覺控制取決於候選召回、資料正確性及後續驗證。

**資料庫有錯誤會怎樣？**  
RAG 很可能放大資料庫錯誤，因為模型是在錯誤候選或錯誤資料的範圍內回答。未來應加入資料來源標記、資料版本、人工審核及異常值檢查。

**與一般 AI 藥物辨識 App 的差異？**  
一般 App 常直接讓 Vision 模型自由辨識；我們的系統多了一層資料庫檢索、候選限制、藥品紀錄回查及用藥安全檢查。這不是優劣比較，而是我們將辨識結果接入台灣藥品資料與風險檢查流程。

## 第 2 題｜RAG 的實際檢索機制

### 回答

目前實作分為兩個階段：

1. **第一階段：刻印與特徵檢索**
   - Gemini 先分析圖片，回傳刻印、顏色與形狀。
   - 系統將刻印交給 `search_by_marking()`。
   - SQLite 使用 `LIKE` 在 `label_front` 和 `label_back` 比對。
   - 完整刻印優先，其餘為模糊包含，再由刻印、顏色、形狀的規則加權評分。

2. **第二階段：候選清單比對**
   - 如果刻印搜尋沒有找到結果，系統會取得最多 500 筆藥品資料。
   - 候選格式包含藥品 ID、刻印、中文名稱、形狀及顏色。
   - 候選清單連同圖片交給 Gemini，由 Gemini 從清單中選擇 3 至 5 個候選。

目前不是 Embedding、FAISS、Cosine Similarity 或向量資料庫；實際方法是 **SQLite 關鍵字與規則式候選搜尋，加上 Gemini 多模態判斷**。

### 評審追問

**第一階段與第二階段差在哪裡？**  
第一階段直接把刻印轉為資料庫查詢，再用規則評分候選，較可驗證、較快且較不受 prompt 候選數影響。第二階段是在刻印檔不到時，由 Gemini 查看有限候選清單與圖片進行綜合判斷。

**為什麼取前 500 筆？**  
主要是為了控制 prompt 長度、token 成本及 API 延遲；500 筆不是已由實驗驗證的最佳候選數，也不代表這些資料就是與照片最相關的候選。未來應在刻印、顏色、形狀或字串相似度上先縮小候選範圍，再比較不同候選數量對召回率與延遲的影響。

**正確藥品不在候選清單怎麼辦？**  
目前沒有可靠機制可以保證識別正確；如果正確藥品不在候選清單，模型只能從現有候選中選較相近者。因此未來實驗應至少記錄候選召回率，以及它是否高於或低於 Gemini 最終排序成功率。

**使用哪種相似度演算法？**  
目前沒有使用向量或數值相似度演算法。第一階段是字串包含與精確匹配優先，第二階段由 Gemini 以多模態能力判斷，並未計算 Cosine Similarity。

## 第 3 題｜如何避免 AI 選錯藥物？

### 回答

目前系統已有部分防護，但不能宣稱已達成完全防錯：

- Gemini 回傳的藥品由資料庫回查確認是否存在。
- 回傳信心度低於預設門檻 `MIN_CONFIDENCE=0.3` 的項目會被過濾。
- 信心度等於或大於 1 的值會被限制為 0.98，不顯示為 100%。
- 辨識後若使用者已登入，會自動執行過敏、重複用藥、交互作用檢查。
- 前端需要明確把辨識結果呈現為「候選」，而不是確定答案。

目前仍缺少兩個關鍵驗證：

1. **候選清單驗證**：尚未完整驗證 Gemini 回傳的 `drug_id` 是否確實存在於當次傳送的候選清單。
2. **特徵一致性驗證**：尚未用資料庫刻印、圖片刻印及形色特徵進行獨立閾值驗證。

因此未來至少應加入：候選集合白名單、刻印編輯距離、同類候選差距檢查、低信心拒答及藥師或醫療人員確認。

### 評審追問

**Gemini 回傳的 ID 一定在候選清單嗎？**  
目前不能保證。程式會依 ID 查資料庫，但沒有強制驗證它是否來自當次候選清單，所以這是需修正的風險。

**沒有特徵驗證嗎？**  
第一階段有刻印、顏色與形狀規則評分；第二階段沒有這類獨立驗證，主要依 Gemini 自行判斷。

**信心度不足怎麼處理？**  
低於目前預設的 0.3 門檻會被過濾，但不一定會進入真正的「無法辨識」狀態。未來應將低信心、候選差距小及候選清單缺漏視為拒答或人工確認案例。

**辨識錯誤會造成用藥風險嗎？**  
會。因此辨識結果不能直接作為服藥決策。正式場景必須結合藥袋核對、藥師確認及不確定性提示。

## 第 4 題｜處方箋 OCR 的總量驗證

### 回答

目前實作使用三個欄位估算期望總量：

```text
期望總量 = 每次劑量 × 每日頻率次數 × 天數
```

例如每次服用 1 顆，每日 3 次，共 3 天，則期望總量為：

```text
1 × 3 × 3 = 9 顆
```

如果 OCR 回傳的數字與期望值差距非常大，且 OCR 值是期望值約 10 倍以上，目前程式會以計算值替代。設計目的是修正典型的 OCR 小數點或數字誤讀，例如 `4.5` 被讀成 `45`。

需要特別說明的是，這套驗證目前是**規則式合理性檢查**，不是替代處方原文的正式處方計算。程式只在 OCR 值明顯異常時修正，沒有對任何約 20% 差異直接拒絕或替換。

### 評審追問

**適用於所有處方箋嗎？**  
不適用。只有劑量、固定頻率及天數三項都能可靠解析時才適用。若頻率為需要時服用、症狀導向、長期用藥、分階段劑量或醫囑本來就有特殊包裝，公式可能不適用。

**醫師開立的總量本來就與公式不同？**  
會保留原值或標示為需人工確認；目前這套規則不是臨床規則引擎。只有極端比例才會修正，正式使用仍需藥師核對。

**如何判斷 OCR 錯誤與特殊用法？**  
目前只能依資料比例與欄位完整性判斷，不能語意判斷特殊處方是否合理。例如單次劑量、頻率及天數被完整抽取時，公式才有參考價值；若是 PRN 或特殊用法，應直接保留原始 OCR 值並人工確認。

**85% 提升至 93% 的數據如何計算？**  
這兩個數字需要有原始實驗樣本、正確判定標準與計算公式才能回溯。若論文中沒有清楚保存修正前後逐筆比對，就不應宣稱為統計上驗證。正確呈現應提供：測試處方筆數、正確筆數、錯誤筆數及是否為固定劑量樣本。正確率公式為：

```text
正確總量筆數 / 有效處方筆數 × 100%
```

## 第 5 題｜四層用藥安全檢查

### 回答

四層由程式規則執行，不是由 AI 直接判斷：

1. **過敏檢查**：取得目標藥物的成分 ID，與使用者的過敏成分比對。嚴重過敏標為 `danger`，其餘過敏標為 `warning`。
2. **重複用藥檢查**：檢查目前使用中的藥單是否已有相同 `drug_id` 或相同藥品名稱。檢查既有藥單時可排除本身。
3. **交互作用檢查**：取得目標藥物與目前活躍藥物的成分，查詢成分配對是否存在於 `drug_interactions`。
4. **嚴重度分級**：任一項為 `danger` 就整體為 `danger`，只有 `warning` 則整體為 `warning`，否則為 `safe`。

資料儲存在 SQLite/SQLAlchemy 的成分、藥物成分關聯、使用者過敏、交互作用及安全檢查紀錄資料表中。

### 評審追問

**不同藥名但有效成分相同如何判斷？**  
目前重複用藊主要比對 `drug_id` 和藥品名稱；交互作用則透過成分多對多關聯比對。如果兩種藥名不同但有效成分相同，重複用藥邏輯未必完全能辨識，應改為以成分集合為主、藥品名稱為輔進行正規化比對。交互作用部分只要兩筆藥品都正確連到成分資料表，理論上可透過成分配對比對，但仍受資料完整性限制。

**交互作用資料來源？**  
目前程式中有 demo 資料與官方資料來源標記，例如 UpToDate、FDA、Lexicomp 及藥品禁忌資料。但這不是完整的臨床商業資料庫，不能宣稱已完成完整藥物交互作用覆蓋。

**資料庫未收錄會怎樣？**  
若成分資料或交互作用不存在，系統可能回傳 `safe`，但實際語意是「資料庫未收錄或無法判定」，不是臨床保證安全。未來應區分 `unknown` 與 `safe`。

**風險分級由 AI 還是規則判斷？**  
由規則判斷：嚴重過敏或 `severe/contraindicated` 交互作用轉成 `danger`，一般警示轉成 `warning`。AI 不負責這層分級。

## 第 6 題｜只有 7 張照片，實驗結果可信嗎？

### 回答

不足以證明 RAG 優於 OpenCV，只能視為小規模可行性觀察。

本次 7 張照片中：

- RAG Top-1 為 42.9%，代表約 3 張第一名正確。
- RAG Top-5 為 100%，代表 7 張照片的正確答案都在前五名。
- Top-5 不是辨識準確率，而是候選召回能力。

7 張樣本只有 14.3% 的離散粒度：成功一張就可能讓 Top-1 變動約 14.3 個百分點。沒有信心區間、統計顯著性、交叉驗證或多次重複，因此不能推論 RAG 對所有藥品或實際環境更準。

目前測試集是否包含光線、角度、背景、模糊及正反面等不同條件，仍需明確列出並保存逐張結果。若沒有統一挑選規則，論文只能說明其為初步示例，而不能宣稱有代表性。

### 評審追問

**為什麼只用 7 張？**  
可回答成：這是初期系統整合與可行性驗證，不是正式臨床驗證。正式結論需要更大規模標註資料。

**照片如何挑選？**  
應實際公開選擇條件：藥品來源、是否有刻印、拍攝環境及是否重複藥品。若沒有事前規劃，不能說是隨機抽樣。

**增加到 100 或 1,000 張會怎樣？**  
結果可能顯著改變，特別是小樣本可能有選樣偏差。應新增：每藥至少多張、按光線角度分層、固定 OpenCV 與 RAG 相同影像集及重複測量。

## 第 7 題｜Top-1 與 Top-5 的差異

### 回答

Top-1 是第一名是否正確，Top-5 是正確藥品是否在前五名候選中。

因此本次：

- Top-1 低，表示系統不能穩定排到第一名。
- Top-5 高，表示正確藥品大多能進入候選集合。

這代表目前系統的**候選召回能力優於最終排序能力**，但也不代表使用者可以安全選藥。Top-5 只有說明候選集合包含正確答案，並沒有驗證使用者能辨別哪一項正確。

研究價值可定位為：驗證 RAG 是否能提升多模態候選召回與資料庫關聯，不可定位為已證明實際辨識準確率。

### 評審追問

**Top-5 是否代表可以安全選擇？**  
不能。前五名仍可能有外觀相似藥品，且沒有人工核對時不能服藥。

**為什麼不直接提高 Top-1？**  
目前候選截取不準確、刻印辨識可能模糊，且缺乏候選重排序機制。應增加刻印編輯距離、候選交叉驗證、圖片特徵比對及 Top-1 信心閾值，才能提升排序能力。

**正確藥排在第五名怎麼辦？**  
應顯示完整候選及理由，不直接預選服用；低信心時要求重新拍攝或人工核對。

**最需要改善召回率還是排序？**  
目前兩者都需要，但優先順序取決於任務：若正確藥常不在候選集合，先改善召回；若正確藥經常在候選集合卻排不在第一名，先改善排序。本次 Top-5 有明顯效果、Top-1 不佳，優先改善的是候選排序與拒答機制。

## 第 8 題｜為什麼 RAG 比 OpenCV 慢？

### 回答

本次實驗 OpenCV 平均 14,171 ms，RAG 平均 22,444 ms，RAG 約慢 8.27 秒。

延遲差異主要來自：

- 圖片上傳及 Gemini API 網路往返。
- Gemini 分析刻印、顏色與形狀。
- SQLite 候選查詢及規則評分。
- 第二階段將候選與圖片再次送給 Gemini。
- 回傳 JSON 的解析與資料庫詳細資料查詢。

不應只說慢了 8 秒。應實際拆分每階段耗時，例如圖片上傳、第一階段 Gemini、SQLite、第二階段 Gemini、資料庫回查及網路往返，才知道瓶頸。

RAG 的價值不是速度，而是候選召回、資料約束及安全檢查整合。但若準確率沒有顯著優於 OpenCV，這種延遲需要重新評估。

### 評審追問

**瓶頸是資料庫、網路還是 Gemini？**  
目前沒有逐階段時間紀錄，無法斷言。不能只憑總時間推測，需要實際執行計時。

**能否快取或平行處理？**  
可以快取藥品特徵、NHI 資料及相同刻印查詢；刻印分析與候選查詢可串接優化，但 Gemini API 網路延遲仍主要受雲端服務影響。

**能否先 OpenCV，再低信心啟動 RAG？**  
可以，這是較合理的混合架構：OpenCV 快速產生候選或低成本特徵，只有模糊、低信心或候選差距小時，再啟動 Gemini RAG。

**如何取得準確度與等待時間平衡？**  
設定 Top-1 閾值、候選差距閾值及超時 fallback；同時比較準確率、召回率、P95 延遲及 API 成本。不能只看平均時間。

## 第 9 題｜系統如何確保藥物資料正確與即時？

### 回答

系統整合兩條資料來源：

- TFDA/健保署公開資料及藥品外觀資料。
- NHI/TFDA 網頁爬蟲取得適應症、主成分、劑型、製造廠及快取資料。

批次更新會將爬蟲或開放資料欄位對應至 SQLite 的 `drugs` 表；使用者查詢時則透過 NHI 快取資料庫加速。快取無資料或過期時，可啟動背景爬蟲補充。

目前的主要限制是：沒有完整的資料版本控制、人工審核紀錄及多來源衝突處理流程。`SEED_INTERACTIONS` 目前是一組 demo 交互作用資料，不應描述成完整臨床資料庫。

### 評審追問

**政府網站格式變更怎麼辦？**  
目前爬蟲可能失效，需要監控欄位、快取失敗率及 HTTP/HTML 差異。未來應加入版本化解析器、欄位完整性檢查、來源快取及重試機制。

**兩個來源資訊不一致怎麼處理？**  
目前沒有完整衝突解決規則。未來應設定政府官方資料優先級、記錄來源與更新時間、保留原始值及人工審核，不能讓自動爬蟲靜默覆蓋。

**更新後怎麼影響既有用藥紀錄？**  
目前若藥品記錄與藥品 ID 連結，既有紀錄可保留；但藥品欄位直接更新可能使歷史紀錄內容變動。未來應保存藥品快照、資料版本及更新前後差異。

**4,419 筆是否足夠？**  
足以建立原型與候選資料庫，但不能證明涵蓋所有台灣常見藥物。專案文件中另有 4,416 筆的說法，正式論文應確認實際資料庫筆數及日期，不應混用數字。

## 第 10 題｜如果真的讓長者使用，你敢讓他依照系統結果吃藥嗎？

### 回答

**我不會讓長者直接依照目前辨識結果服藥。**

目前系統最大的風險是辨識錯誤、候選召回不完整及缺少臨床驗證。特別是：

- RAG Top-1 只有初步小樣本準確率。
- 候選清單可能漏掉正確藥品。
- RAG 是否正確選中候選尚缺完整的獨立驗證。
- 缺成分或交互作用資料時可能無法判定，不能視為安全。
- AI 不具備個人完整病史、腎肝功能及劑量個體差。

正式投入前至少需要：

1. 大規模、分層且標註完整的藥品影像測試集。
2. 候選集合驗證、刻印容錯及低信心拒答。
3. 完整且來源可追溯的藥物與交互作用資料庫。
4. 藥師與醫師參與規則審核及病例驗證。
5. 不確定性提示、重新拍攝、人工核對及緊急諮詢流程。
6. 臨床場域測試、事件紀錄與責任機制。

### 評審追問

**責任如何界定？**  
正式醫療決策責任不能完全交給系統。應採醫療器材法規、使用者同意、風險告知、醫療專業審核及事後追溯紀錄等機制，責任依實際開發、運營及醫療使用角色界定。

**如何讓長者知道結果可能錯？**  
介面要用大字、明顯警語與視覺提示，例如「僅供辨識參考，不可直接服藥」，並提供重新拍攝及連絡藥師入口。

**需要藥師或醫療人員參與嗎？**  
需要。藥師可核對藥袋與刻印、處方及個人用藥；醫師可負責不明確劑量、特殊處方及高風險交互。

**未來如何臨床驗證？**  
使用多醫療院所參與、相同標準影像集及盲測；同時記錄 Top-1、Top-5、召回率、人工介入率、誤辨率、延遲、P95 時間及實際用藥事件。正式臨床驗證應包括計畫審查、知情同意及長者可理解的操作流程。
